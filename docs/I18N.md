# Internationalization and the English/Amharic Content Contract

| Field | Value |
| --- | --- |
| Status | Mandatory architecture requirement for every phase |
| Locales | `en` (English), `am` (Amharic) |
| Default locale | `en` |
| URL strategy | `/{locale}/...`; root redirects by preference |
| Content rule | Every administrator-managed public field stores English **and** Amharic |
| Admin rule | Every admin form asks for both language values and blocks publishing until complete |
| Legal rule | Legal/policy translations require human review; no machine translation in production |

## 1. Non-negotiable requirement

Amharic is not a later add-on and not a machine-translation layer. It is part of the data model, the admin workflow, the API contract, the UI, the emails and the tests.

Specifically:

1. The public UI is fully available in English and Amharic.
2. Users can switch language from the public site and the dashboard without losing their page/context.
3. Administrator-entered data has **two fields for every translatable value**: English and Amharic.
4. When an administrator uploads a destination, category, travel plan, selection event, FAQ, banner, policy or image, the form asks for the Amharic text (name/title/description/alt text/terms, as applicable) at the same time.
5. “Publish” is blocked if required Amharic content is missing or incomplete. Draft saving is allowed so translation work can happen over time.
6. Amharic appears correctly with Ethiopic typography, Unicode normalization, line wrapping and locale-aware formatting.
7. Automated tests check dictionary key parity, published-content completeness and both-language form flows.

The platform will not display an Amharic page containing untranslated English admin content as though it were translated. Missing translations are an admin/content defect and are visible in the CMS.

## 2. URL and locale strategy

### 2.1 Locale-prefixed routes

All pages live under `app/[lang]/` and are served at:

```text
/en
/en/destinations
/en/destinations/simien-mountains
/en/travel-plans
/am
/am/destinations
/am/destinations/simien-mountains
/am/travel-plans
```

`lang` is validated against the supported locale allowlist. An unsupported prefix returns 404 (or redirects to the preferred locale for the unprefixed root only).

### 2.2 Root behaviour

Requests to `/` are handled by `proxy.ts`:

1. If a valid `lte_locale` cookie exists, redirect to that locale.
2. Otherwise, negotiate `Accept-Language` safely; default to `en`.
3. Issue a `302` redirect, not a permanent one, so the user can switch later.
4. Persist the chosen locale in a non-sensitive, year-long cookie (`SameSite=Lax`).

The required routes from the brief map to the locale-prefixed equivalents. For example, `/destinations` is served as `/en/destinations` and `/am/destinations`. Root `/` remains the entry point and redirects. Locale prefixes are an approved adaptation because they produce stable, indexable, SSR-friendly bilingual URLs.

### 2.3 Language switcher

- Available in the public header/footer and dashboard/admin shells.
- Selecting a language navigates to the equivalent route in the other locale while preserving the path, query string and safe fragment.
- Example: `/en/destinations?category=heritage&page=2` → `/am/destinations?category=heritage&page=2`.
- If a localized equivalent route does not exist, fall back to that locale’s section landing page and show a notice.
- The switch writes the locale cookie and, for signed-in users, updates `preferredLocale` after an authenticated server action.
- The current page’s `<html lang>` and metadata are updated by the server-rendered layout; do not mutate the DOM `lang` only on the client.
- Route slugs remain language-neutral (`simien-mountains` in both locales), avoiding duplicated slug lookup and redirect complexity.

### 2.4 SEO

- Each page emits a canonical URL for the current locale.
- `hreflang` alternates link `en`, `am` and `x-default`.
- Sitemaps include both locale variants for published content.
- Metadata (`title`, `description`, Open Graph, image alt) comes from the localized fields, not from a single English fallback on published pages.
- Structured data includes the language/name appropriate to the page.

## 3. Localized content data contract

```ts
export type Locale = "en" | "am";
export type LocalizedText = {
  en: string;
  am: string;
};
```

- Stored in MongoDB as an embedded object `{ en, am }` with `_id: false`.
- API/Server Action payloads accept the same shape; flat ad-hoc fields such as `nameAm` are not accepted at service boundaries.
- The CMS form model may use nested field names (`name.en`, `name.am`) for React Hook Form, but persists one canonical object.
- `slug` is deliberately not localized.
- Rich text is sanitized once per locale using the same allowlist before persistence.
- Search indexes include both languages. Amharic search quality is explicitly tested; Atlas Search is preferred, with a documented fallback.

### 3.1 Required dual fields by entity

| Entity | English + Amharic required before publish |
| --- | --- |
| Destination | name, short description, full description, region, city, price note, opening hours, best time to visit, accessibility, travel tips, SEO title, SEO description, main image alt, every gallery image alt/caption |
| Category | name, description, image alt, SEO title, SEO description |
| Travel plan | name, summary, description, inclusions, exclusions, eligibility text, rules, refund policy, cancellation policy, tax label |
| Selection event | name, description, public rules, prize/trip terms, refund policy, cancellation policy |
| Selection result | public summary/verification explanation if shown as prose |
| Content entry | title, subtitle, body, CTA label, image alt, SEO fields as applicable |
| FAQ | question and answer |
| Homepage section/banner | heading, supporting text, CTA label, image alt |
| Policy/legal pages | title and body after human translation/legal review |
| Notification/email template | subject/title and body |
| Contact/social content | only prose labels; phone/email/URL values are not translated |
| Image/media | alt text and caption (caption when used) |

Data values that are not language-dependent (phone numbers, coordinates, URLs, prices, dates) are stored once. Proper nouns may legitimately be the same in both languages, but the Amharic field must still be explicitly filled or the content cannot publish.

### 3.2 What is not machine-translated

- Terms and conditions, privacy policy, refund/cancellation terms, selection rules, eligibility rules and legal disclaimers require a human legal/translation review.
- The platform does not call a translation API on publish.
- An optional future “copy English” convenience may only copy into the Amharic field for non-legal short labels and must show a confirmation warning; it must never silently create a published translation.
- User-generated reviews/support messages are not auto-translated. They display in their original language, with an explicit language tag.

## 4. Administrator experience

### 4.1 Dual-language fields

The admin UI uses a shared `LocalizedFieldGroup` (and `LocalizedRichTextField`, `LocalizedImageAltField`) component:

- Desktop: English and Amharic fields side by side, each labelled with its language name and `lang` attribute.
- Mobile: stacked, with a clear language badge and sticky completeness indicator.
- Long-form content: an EN/AM tab switch is allowed for screen space, but both fields are part of the same required form and completeness is always visible. The Amharic field is never hidden behind an “optional translations” section.
- Each field shows:
  - label in the current admin UI language,
  - explicit `English` / `አማርኛ` tag,
  - character count and limit,
  - inline validation in the admin’s chosen language,
  - an `lang="am"` attribute for correct screen-reader pronunciation,
  - a missing/copied/unreviewed status where relevant.
- Amharic labels in the form itself are provided when the admin UI is set to Amharic; English labels remain available when requested.

Example field pair:

```text
Destination name / የመዳረሻ ስም
[ English ]  Example destination
[ አማርኛ ]    ምሳሌ መዳረሻ
```

(Example text only; no real destination fact is asserted.)

### 4.2 Publish vs. draft

- `Save draft` allows incomplete translations and shows `Amharic missing` warnings.
- `Publish` / `Activate` runs a server-side translation-completeness check.
- If any required localized field is empty, publishing fails with a field-level, localized error. The admin can fix the exact fields; a generic “validation failed” message is not enough.
- A content list shows completeness badges (`EN ✓ / AM ✓`, `EN ✓ / AM —`) and supports filtering by missing Amharic.
- Bulk actions cannot publish incomplete content.
- Image upload dialogs ask for English and Amharic alt text; upload can complete first, but publishing the owning content requires the alt text in both languages.

### 4.3 Admin interface translation

- Admin navigation, buttons, validation messages, empty states and confirmation dialogs are bilingual.
- The admin can run the entire CMS in Amharic while entering Amharic content.
- Admin-only terminology (snapshot, reconciliation, eligibility snapshot) has a reviewed bilingual glossary so translations remain consistent.
- The locale switcher is available in the admin header and preserves the current page.

### 4.4 Translation workflow and audit

- Content entries track `translation missing` as an operational report.
- Policy/legal content records `legalReview` metadata (reviewer reference, date, approval reference) before publishing in either language.
- Admin edits that change published legal terms create a new terms version/hash; existing orders retain the version accepted at purchase.
- Every publish/unpublish/reorder action is audit-logged with the actor and previous/next state hashes.

## 5. Public UI implementation rules

### 5.1 Dictionaries, not duplicated components

- UI strings live in `messages/en.json` and `messages/am.json`.
- A typed `getMessages(locale)` server helper loads the dictionary. Server Components read the locale through the route param or `next/root-params`.
- Components do not branch on `locale === 'am'` to hardcode strings.
- Translation keys are structured by feature (`nav.*`, `auth.*`, `destinations.*`, `plans.*`, `payments.*`, `selection.*`, `admin.*`, `validation.*`).
- Tests assert both dictionaries have identical key sets and no empty values.
- Server-side validation uses stable error codes (e.g. `AUTH_INVALID_CREDENTIALS`) and resolves them to localized messages at the boundary; Zod schemas do not embed one language’s prose.

### 5.2 Typography and layout

- Use a self-hosted Ethiopic-capable font (e.g. Noto Sans Ethiopic) with the existing brand sans font. Do not rely on the browser to find a suitable font.
- Ensure Ethiopic combining marks render correctly; preserve Unicode and normalize only for comparisons/search, never by destructively rewriting stored content.
- Allow generous line-height for Amharic. Avoid letter-spacing, all-caps transforms and truncation that clips Ethiopic glyphs.
- Test long Amharic strings in navigation, cards, buttons, tables, dialogs and mobile viewports.
- Amharic is left-to-right; do not apply RTL layout. Set `lang="am"` and `dir="ltr"`.
- Numbers, currency and dates use `Intl` with the locale. Currency is ETB. Times are displayed in `Africa/Addis_Ababa`.
- The Ethiopian calendar is an optional, feature-flagged presentation (default off) until product review approves it. Do not force Gregorian-only claims without review.
- Reduced-motion and accessible focus behaviour apply equally to both languages.

### 5.3 Error and empty states

- All user-facing validation, 404, unauthorized, empty, payment-pending and selection states have Amharic messages.
- API errors never expose raw database/provider messages. They carry stable codes and localized messages.
- Toast/screen-reader announcements use the active locale.

## 6. Notifications, email and SMS

- Store notification title/body as `LocalizedText`; render in the recipient’s `preferredLocale`.
- Email templates are bilingual; subject and body come from the locale-specific template or localized content.
- Critical account-security messages should include a security notice in the user’s language and remain understandable if formatting is unavailable.
- A user with `preferredLocale=am` receives Amharic notifications by default; they can change it in settings.
- SMS templates are short and reviewed separately; provider encoding and character limits must be tested for Ethiopic text.
- No notification reveals private data about another participant/winner.

## 7. Search, validation and formatting

| Concern | Rule |
| --- | --- |
| Search | Index both languages; test Amharic queries with/without Ethiopic punctuation; do not expose raw regex scans. |
| Sorting | Use locale-aware collation where alphabetical sorting is offered; otherwise sort by explicit admin display order/date. |
| Dates | Store UTC; display `Africa/Addis_Ababa`; use locale-specific `Intl.DateTimeFormat`. |
| Currency | Integer santim in storage; `Intl.NumberFormat(locale, { style: "currency", currency: "ETB" })` for display. |
| Slugs | Language-neutral, ASCII-safe; display names remain localized. |
| SEO | Localized title/description, canonical URL and hreflang; no duplicate-language content claiming to be translated. |
| Validation | Stable error codes + localized resolver; field names/labels localized. |
| File names | Random opaque object keys; never use an Amharic filename as a storage path. |

## 8. Content completeness enforcement

The service layer exposes a shared validator:

```ts
type PublishCheck = {
  entity: string;
  missing: Array<{ field: string; locale: "en" | "am" }>;
  legalReviewRequired: boolean;
};

function assertPublishable(entity, localeFields, options): PublishCheck;
```

- Called by every publish/activate action (destination, category, plan, event, content entry).
- Runs on the server even if the client form says “valid”.
- Returns field-level errors with stable codes so the UI can render both localized labels and messages.
- Writes a `content_publish_blocked` audit/telemetry event for operational visibility (no sensitive content in logs).
- A scheduled admin report lists published content missing either language; ideally zero after publish (legacy/import exceptions must be fixed).
- Database migrations/import scripts cannot bypass this check for published status.

## 9. Bilingual acceptance criteria

- [ ] `/en` and `/am` render the same information architecture with correct `lang` attributes.
- [ ] The language switcher preserves the current page and query string.
- [ ] Navigation, buttons, validation messages, empty states, errors, payment states and selection states exist in both locales.
- [ ] Every administrator content form shows English and Amharic inputs for all required fields.
- [ ] Publishing is blocked until all required Amharic fields are complete.
- [ ] Image upload asks for both alt texts.
- [ ] Legal/policy content records human review before publish.
- [ ] Both dictionaries pass key-parity and empty-value tests.
- [ ] Amharic glyphs are not clipped in cards, tables, dialogs or buttons at 320 px, 375 px, 768 px and 1440 px.
- [ ] Screen readers receive `lang="am"` for Amharic content and forms.
- [ ] Amharic search returns expected results in integration/E2E tests.
- [ ] Notification/email templates render in the user’s preferred locale.
- [ ] No machine translation is silently applied to legal or admin-managed content.

## 10. Open translation decisions

1. Who performs the human review of Amharic legal/policy content, and what reference is recorded?
2. Should the Ethiopian calendar be offered by default? Current default: off.
3. Is an optional “copy English into Amharic” action acceptable for short non-legal labels, or should every Amharic field be typed from scratch? Current default: no copy action in production; admins type or paste reviewed translations.
4. Which SMS provider supports Ethiopic/Unicode correctly and at what segment cost? Required only if SMS is enabled.
5. Are destination names in Amharic sourced from official tourism authorities? The CMS requires an admin-entered value and does not invent one.

## 11. Translation review status

Initial UI strings added in Phase 2 will be marked as **draft Amharic**. Before production, a native Amharic reviewer must review the dictionaries, especially payment, legal, eligibility, account-security and selection terminology. The reviewer’s approval is recorded in the launch checklist. Automated tests protect structural completeness, not translation quality.
